1The project in one page

The task. Given a sentence in Malayalam, find every name in it and say what kind of name it is: a person (PER), an organization (ORG) or a location (LOC). This task is called Named Entity Recognition (NER).

തിരുവനന്തപുരത്ത് LOC നടന്ന ചടങ്ങിൽ കേരള LOC മുഖ്യമന്ത്രി പിണറായി വിജയൻ PER സംസാരിച്ചു .

"At a function held in Thiruvananthapuram, Kerala Chief Minister Pinarayi Vijayan spoke." (real output of our model)

What we built. We took a pre-trained Indian-language Transformer, ai4bharat/IndicBERTv2-MLM-only, and fine-tuned it on 50,000 Malayalam sentences from the Naamapadam dataset. We trained two versions with different output layers:

  • Baseline (same idea as the base paper): a linear layer + softmax that labels each word on its own, trained with class-weighted cross-entropy.
  • Proposed (our extension): the same encoder with a Conditional Random Field (CRF) on top, which labels the whole sentence jointly and learns which tag can follow which.

Then we evaluated both on the human-annotated test set with strict entity-level F1, and wrapped the better model in a Gradio web app and a FastAPI REST service.

2What Named Entity Recognition is

A named entity is a real-world object that has a proper name: a person (പിണറായി വിജയൻ), an organization (ഐഎസ്ആർഒ, ISRO), a place (കൊച്ചി, Kochi). Some datasets also count dates, money, numbers, products or events. Our dataset, Naamapadam, labels only three types: PER, ORG, LOC.

NER has two jobs at once:

  1. Detection (segmentation): where does a name start and end? "Kerala Blasters" is one name of two words.
  2. Classification (typing): what type is it? "Kerala" alone is LOC, but inside "Kerala Blasters" it is part of an ORG.

NER as sequence labelling

The standard trick is to turn "find spans" into "give every word a tag". If a sentence has words x₁ … xₙ, the model outputs one tag y₁ … yₙ. This is called sequence labelling (the same framing as part-of-speech tagging).

The IOB2 tagging scheme

To mark where a multi-word name starts and stops, each word gets one of:

  • B-X: Beginning (first word) of an entity of type X
  • I-X: Inside an entity of type X (second word onwards)
  • O: Outside any entity

With 3 types we get 3 × 2 + 1 = 7 tags. Our config.py numbers them exactly as Naamapadam does:

The rule that matters later

In IOB2, I-X is legal only right after B-X or I-X of the same type. O → I-PER or B-LOC → I-ORG are invalid transitions. A model that tags each word independently can produce them. A CRF learns to avoid them. This is the core reason for our CRF extension.

Other schemes you may be asked about

  • IOB1 (the original CoNLL-2003 style): B- is used only when two entities of the same type are adjacent; otherwise every entity word is I-. IOB2 is cleaner because every entity starts with B-.
  • BIOES / BILOU: adds E- (end) and S- (single-word entity). More tags, more explicit boundaries; it sometimes helps slightly, but our dataset ships in IOB2, so we kept it.
Panel questions§2 NER basics
Why model NER as token classification instead of directly predicting spans?

It turns a hard structured problem (choose start, end and type for any number of spans) into a simple one (one label per word) that standard classifiers and BERT's token-classification setup handle directly. The IOB2 tags still encode the spans exactly, so nothing is lost. Span-based models exist (they score every possible span), but they are heavier and the standard benchmark format is IOB2.

Why do we need B- and I- tags at all? Why not just PER, ORG, LOC, O?

Without B-, two different names side by side would merge. "ഷബീന ഖാൻ , തുഷാർ കപൂർ" is separated by a comma, but in lists without punctuation, or names like "Akshay Kumar's Cape of Good Films", two adjacent entities of different or same types need a boundary marker. B- marks where each new entity begins.

Why only PER, ORG and LOC? What about dates and numbers?

Naamapadam, the largest public Indic NER dataset, annotates only these three types, so the neural model can only learn these. For the demo we added DATE and CARDINAL with a rule-based regex layer (section 19). Those rules are not included in any reported metric.

Why did you choose IOB2 and not BIOES?

The dataset is distributed in IOB2, seqeval scores IOB2 directly, and the base paper and IndicNER also use it, so results stay comparable. Converting to BIOES would add 6 more tags (13 total), make the CRF transition matrix larger and spread the already small I-LOC/I-ORG data over more classes. The CRF already captures most of the boundary structure that BIOES makes explicit.

What is the difference between NER and POS tagging?

Both are sequence labelling. POS tagging labels every word with its grammatical category (noun, verb…), so every word gets a meaningful tag. NER labels only proper-name spans; most words are O. That is why NER has a severe class-imbalance problem (74% of our tokens are O) and needs span-level evaluation.

3Why Malayalam is hard for NER

Malayalam is a Dravidian language spoken mainly in Kerala, written in its own Brahmic script. Four properties make NER hard:

1. No capital letters

In English, "Apple" vs "apple" is a strong hint that a word is a name. Malayalam script has no upper/lower case, so this cue does not exist. The model must rely on context and on the word itself.

2. Agglutination (words glue together)

Malayalam attaches case markers, postpositions and even other words to the end of a stem, making one long word. The same city appears in many surface forms:

Surface formMeaning
തിരുവനന്തപുരംThiruvananthapuram (base form)
തിരുവനന്തപുരത്ത്in Thiruvananthapuram (locative)
തിരുവനന്തപുരത്തേക്ക്to Thiruvananthapuram
തിരുവനന്തപുരത്തിന്റെof Thiruvananthapuram
കുമാറിൻറെKumar's (name + genitive)

A word-level vocabulary would treat these as unrelated words, and many forms would be rare or unseen. A subword tokenizer splits words into reusable pieces (section 6). Our model labels the whole agglutinated word (തിരുവനന്തപുരത്ത് = B-LOC), which matches how Naamapadam annotates.

3. Ambiguity

  • Many person names are also ordinary words (for example വിജയൻ relates to vijayam, victory; names like Sundaram, Lakshmi, Kala are common words or concepts).
  • Organization names often contain a place: കൊച്ചി മെട്രോ റെയിൽ ലിമിറ്റഡ് (Kochi Metro Rail Limited), Kerala Blasters. The first word looks like LOC but is B-ORG. Our confusion matrix shows exactly this error (12 B-ORG → B-LOC).
  • Free word order: Malayalam is mostly SOV but flexible, so position is a weaker cue than in English.

4. Low resource

Before Naamapadam (2023), Malayalam NER systems were trained on a few hundred hand-labelled sentences (for example the Fuzzy SVM paper used a 500-sentence in-house test set). Pre-trained multilingual models and large projected datasets changed this.

Script details you may need

A Malayalam "letter" you see on screen is often several Unicode code points: a consonant + virama (്) + another consonant forms a conjunct, and vowel signs attach to consonants. These visual units are called grapheme clusters. If you cut text at the wrong code point you break a character. That is why predict.py splits text only on whitespace and punctuation (never inside a word), and the comment says "without breaking Indic glyph clusters". Malayalam also has its own digits (൦–൯, U+0D66–U+0D6F), which our CARDINAL regex handles.

Panel questions§3 Language challenges
How does your system handle agglutination? You didn't use a morphological analyser.

In two ways. (1) The WordPiece tokenizer splits long words into frequent pieces, for example ഉപമുഖ്യമന്ത്രിയാകും → ഉപമുഖ്യമന്ത്രി + ##യാകും, so the stem is shared across inflected forms. (2) BERT's self-attention lets the first subword's vector see the suffix pieces and the neighbouring words, so the case marker informs the decision. We label each word through its first subword. This avoids a morphological analyser, which for Malayalam is error-prone and slow, and would introduce its own mistakes into the pipeline.

Why not stem or lemmatize words first and then tag?

The gold labels are on surface words (തിരുവനന്തപുരത്ത് is B-LOC as a whole), so we must output tags on surface words anyway. Stemming would discard the case suffix, which is useful context (a locative suffix suggests a place). Good Malayalam stemmers are also not readily available, and errors would compound. Subword tokenization gets most of the benefit for free.

Does the lack of capitalization really matter for a BERT model?

Yes. Studies on English show cased models do better on NER than uncased ones, because case is a strong signal. In Malayalam that signal never existed, so the model depends entirely on context and the word's form. This is one reason Malayalam NER scores are lower than English (English CoNLL-2003 F1 is above 92 for BERT models).

Why is ORG the hardest entity type in Malayalam?

Organization names are long (many have 3+ words), often contain place names (Kochi Metro, Kerala Blasters) or common nouns (bank, party, company), are transliterated from English, and are fewer in the data (16,265 ORG mentions vs 35,057 PER in our training subset). In Naamapadam the training labels are projected from English, and ORG boundaries are the noisiest. Every Malayalam NER paper, including our base paper, reports ORG as the weakest class.

Panel questions§4 Choice of approach
Why not use a rule-based or dictionary (gazetteer) approach?

Names are an open set: new people, companies and places appear every day. Gazetteers cannot cover them, and agglutination means a dictionary would need every inflected form. Rules also cannot resolve ambiguity (is കേരള LOC or part of an ORG?). We do use rules, but only where they are reliable: dates and numbers in the demo overlay.

Why not BiLSTM-CRF, which is cheaper?

A BiLSTM-CRF learns everything from the labelled data. A pre-trained Transformer already knows Malayalam from billions of words of raw text (IndicCorp v2), so it needs far less labelled data and handles rare words better. In published benchmarks, fine-tuned BERT models beat BiLSTM-CRF on NER in nearly every language. We kept the best idea of BiLSTM-CRF, the CRF layer, and replaced the LSTM with BERT.

Why not just use ChatGPT or another LLM?

(1) Cost and latency: an LLM call per sentence is slow and paid; our model runs locally in milliseconds. (2) Malayalam is low-resource in LLM training data and tokenization is inefficient. (3) We need exact word-level spans for evaluation; LLMs often paraphrase or miss boundaries. (4) The course asks us to implement and analyse a method, not call an API. A 278M-parameter fine-tuned encoder is the standard strong choice for this task.

Why not an SVM like the Fuzzy SVM paper, which reported 88.13%?

That system needed a parser, hand-written grammar rules and features, and was tested on 500 private sentences, so its number cannot be reproduced or compared. Our model needs no hand-made features, works on any Malayalam text, and is evaluated on a public, human-annotated benchmark with a strict metric.

5Transformers and BERT, from zero

Step 1: words become vectors

A neural network only works with numbers. Each subword in the vocabulary gets an ID, and the model looks up a learned vector for it (an embedding). In IndicBERTv2 each vector has 768 numbers. A position embedding is added so the model knows word order, and a segment embedding marks sentence A/B. Similar words end up with similar vectors after training.

Step 2: self-attention, the key idea

The meaning of a word depends on its neighbours. In "കേരള Blasters", "Kerala" should look at "Blasters" to realise it is part of an organization. Self-attention lets every word look at every other word in the sentence and mix in information from the relevant ones.

For each word, the model computes three vectors from its embedding with learned matrices:

  • Query (Q): "what am I looking for?"
  • Key (K): "what do I contain?"
  • Value (V): "what information do I pass on?"

Word i compares its query with every word's key (a dot product). High score = relevant. Softmax turns scores into weights that sum to 1, and the output is the weighted average of the values:

Attention(Q, K, V) = softmax( Q·Kᵀ / √d_k ) · V d_k = size of each key vector (64 per head in BERT-base) dividing by √d_k keeps the dot products from growing too large, so softmax stays smooth

Multi-head attention runs 12 of these in parallel ("heads"), each free to learn a different relationship (one may track the previous word, another the verb, another suffixes). Their outputs are concatenated.

Step 3: stack layers

One Transformer encoder layer = multi-head self-attention → add & layer-norm → a small feed-forward network (768 → 3072 → 768) → add & layer-norm. The "add" parts are residual connections, which let gradients flow through deep stacks. BERT-base stacks 12 layers. After layer 12, every subword has a 768-number vector that encodes the word in its context. These are the vectors h_i our classifier reads.

Step 4: BERT pre-training

BERT (Bidirectional Encoder Representations from Transformers, Devlin et al., 2019) is a Transformer encoder pre-trained on raw text with a self-supervised task:

  • Masked Language Modelling (MLM): hide 15% of tokens and train the model to guess them from both sides. To guess a hidden word well, the model must learn grammar, meaning and world knowledge. No human labels are needed, so it can train on billions of words.
  • Original BERT also used Next Sentence Prediction (NSP). Later models (RoBERTa, IndicBERTv2) dropped it. That is what "MLM-only" in IndicBERTv2-MLM-only means: pre-trained only with masked language modelling on monolingual text.

Bidirectional is the important word: unlike GPT, which reads left to right, BERT sees the whole sentence at once. For tagging a word, both left and right context matter, so an encoder like BERT is the natural choice.

Step 5: fine-tuning

We put a small new layer on top of the pre-trained model (here a 768 → 7 linear layer, plus optionally a CRF) and train everything on our labelled NER data for a few epochs with a small learning rate. The pre-trained knowledge is reused; only a little task-specific learning is needed. This is transfer learning.

Panel questions§5 Transformers
Explain self-attention in simple terms.

Every word asks a question (query), every word advertises what it has (key), and the word collects information (values) mostly from the words whose keys match its query. The formula is softmax(QKᵀ/√d)·V. It lets a word like കേരള see ബ്ലാസ്റ്റേഴ്സ് and change its representation from "place" to "part of a team name".

Why divide by √d_k?

Dot products of long vectors grow with their length. Very large scores push softmax into a region where one weight is ≈1 and the rest ≈0, and gradients become tiny. Dividing by √d_k keeps scores in a reasonable range so training is stable.

Why BERT (an encoder) and not GPT (a decoder)?

NER needs context from both sides of a word. GPT-style decoders use causal attention and see only the left context when computing a token's representation. BERT's bidirectional attention sees the full sentence, which is why encoder models dominate token-classification tasks.

What happens to BERT's weights during fine-tuning? Did you freeze anything?

No layers are frozen. AdamW(model.parameters(), …) updates all encoder weights plus the new linear layer and CRF. Full fine-tuning gives the best accuracy when there is enough data (we have 50k sentences). The small learning rate (3e-5) and warm-up keep the pre-trained knowledge from being destroyed early on.

How many parameters does your model have, and where are they?

About 278M. A large share sits in the embedding table: 250,000 vocab × 768 ≈ 192M. The 12 Transformer layers add about 85M (≈7M each). Our new head is tiny: the linear layer has 768 × 7 + 7 = 5,383 parameters and the CRF has 7 × 7 + 7 + 7 = 63.

What is the maximum input length and why 128?

BERT supports up to 512 positions. Our sentences average about 9 words, ~14 subwords (fertility 1.56), so 128 covers almost all sentences while keeping memory and time low: attention cost grows with the square of the length. Only 2 of 8,534 test words were cut by truncation (8,532 words were scored).

6Subword tokenization (WordPiece)

A model needs a fixed vocabulary. Three options:

  • Word-level: every distinct word is a token. For Malayalam this explodes because of agglutination, and any unseen word becomes [UNK] (unknown).
  • Character-level: tiny vocabulary but very long sequences and weak meaning per token.
  • Subword-level (WordPiece, BPE, SentencePiece/Unigram): frequent words stay whole, rare words split into frequent pieces. Best of both. Every word can be represented, so there is essentially no [UNK].

WordPiece (used by BERT, mBERT, MuRIL and IndicBERTv2) builds its vocabulary by starting from characters and repeatedly merging the pair of pieces that most increases the likelihood of the training corpus. At tokenization time it greedily takes the longest piece in the vocabulary from the left. Pieces that continue a word are marked with ##.

Fertility = average number of subwords per word. On our test set it is 1.56. Lower fertility means the vocabulary fits the language well (mBERT's fertility on Indian languages is much higher because Malayalam got only a small slice of its 119k vocabulary). IndicBERTv2 has a 250,000-token vocabulary built for Indic scripts.

Panel questions§6 Tokenization
What is subword fertility and why did you measure it?

Fertility = subwords ÷ words. We measured 1.56 on the test set (compare_models.py and notebook 01). It tells us (1) how well the tokenizer fits Malayalam: lower is better, (2) how much the word/label alignment matters: with 1.56, about a third of all subword positions are continuation pieces that must be masked, and (3) that 128 subwords is plenty for ~9-word sentences.

Why not split into words and use word embeddings like word2vec/fastText?

Static word embeddings give one vector per word regardless of context ("Kerala" the state vs "Kerala" in Kerala Blasters get the same vector) and fail on unseen inflected forms. fastText helps with character n-grams but is still context-free. BERT's contextual subword vectors solve both problems.

What is the difference between WordPiece, BPE and SentencePiece?

BPE merges the most frequent adjacent pair; WordPiece merges the pair that most increases corpus likelihood; SentencePiece is a library that treats text as a raw character stream (including spaces) and can run BPE or the Unigram algorithm, which starts big and prunes. XLM-R uses SentencePiece; BERT-family models, including IndicBERTv2, use WordPiece with ## markers.

Could the tokenizer split a word in the middle of a Malayalam character?

WordPiece works on Unicode code points, so in principle a piece boundary can fall between a consonant and its vowel sign. That does not break anything for the model, because the pieces are only IDs. It only matters for display, and we never display subwords: we always map predictions back to whole words using word_ids().

7Multilingual encoders: which one and why

Training BERT from scratch for Malayalam alone would need huge text and compute. Instead we use a model pre-trained on many languages at once. 8Softmax, cross-entropy and class imbalance

From vector to tag scores

The encoder gives each subword a 768-number vector h_i. A linear layer turns it into 7 numbers, one per tag. These raw scores are called logits (or emission scores in CRF language):

e_i = W · Dropout(h_i) + b W is 7 × 768, b has 7 numbers

Softmax

Softmax turns the 7 scores into probabilities that are positive and sum to 1:

p(tag c | word i) = exp(e_i,c) / Σ_k exp(e_i,k) example: scores O=2.0 B-PER=1.0 I-PER=0.1 … probs O=0.63 B-PER=0.23 I-PER=0.09 … → predict O (argmax)

The softmax baseline predicts argmax for each word independently. It never looks at what tag it chose for the previous word.

Cross-entropy loss

Training pushes the probability of the correct tag towards 1. The loss for one word is −log p(correct tag): if the model gives the right tag probability 0.9, loss = 0.105; if 0.1, loss = 2.30. The loss over a batch is the average.

The class-imbalance problem

In our training subset, 74.1% of words are O and only 0.9% are I-LOC. A lazy model that always says O already gets 74% accuracy and finds zero entities. The model is pulled towards O because O dominates the loss.

Our fix for the baseline: inverse-frequency class weights

get_class_weights() in src/model.py counts each tag and gives rare tags bigger weights:

w_c = N / (K · n_c) N = total words, K = 7 tags, n_c = count of tag c then divide all weights by the largest one, so the rarest tag gets weight 1.0 weighted loss = Σ_i w_(y_i) · (−log p(y_i)) / Σ_i w_(y_i) (PyTorch's 'mean' with weights)

Panel questions§8 Loss and imbalance
Why did you use class weights? What problem do they solve?

74% of tokens are O. Plain cross-entropy lets the model reach low loss by favouring O, which gives poor recall on entities, especially rare tags like I-LOC (0.9%). Inverse-frequency weights make each rare-tag mistake cost more, so the model pays attention to entities.

Did the class weights actually help?

Partly. The softmax model has high recall (81.1%) but low precision (65.1%). The weights over-corrected: an I-LOC weight 86× larger than O made the model tag too many words as I-LOC/I-ORG. Linear I-LOC token precision is only 36%. Weights trade precision for recall; they don't fix the structural problem. The CRF gives balanced P/R (84.5/84.1) without any weights. A softer weighting (e.g. square-root of inverse frequency) or no weights might have given the softmax baseline a better F1. We did not run that ablation; it is in future work.

Why weights rather than oversampling, undersampling or focal loss?

Imbalance in NER is inside each sentence: every sentence is mostly O, so you cannot oversample "entity sentences" without still getting mostly O tokens. Undersampling O words would break sentences. Class weights are the simplest token-level fix, cost nothing extra and are one argument in nn.CrossEntropyLoss. Focal loss (down-weights easy examples) is a reasonable alternative we could try.

Why normalize the weights by the maximum?

Only the ratios between weights change what the model learns. Dividing by the maximum keeps all weights in (0, 1] so the loss stays on a familiar scale and the learning rate behaves normally. PyTorch's weighted mean also divides by the sum of weights, so the absolute scale mostly cancels anyway.

Why is the CRF not trained with class weights?

The CRF loss is the log-probability of the whole tag sequence, not a sum of independent per-word losses, so per-class weights don't plug in directly (the pytorch-crf library has no weight option). Also, the CRF's transition scores already handle a lot of what weighting tries to fix. A consequence: our two models differ in both decoder and weighting, so the +12 F1 is the effect of both together. We state this in the report.

What is the 1e-5 in counts + 1e-5?

A tiny number to avoid dividing by zero if some tag never appears in the training subset. With 50k sentences every tag appears, so it has no practical effect.

9Conditional Random Fields and Viterbi

The problem with tagging words one at a time

The softmax head picks the best tag for each word separately. Suppose for "പിണറായി വിജയൻ സംസാരിച്ചു" (Pinarayi Vijayan spoke) it is unsure about the first word and picks O, then confidently picks I-PER for the second. Result: O, I-PER, O. That is an invalid sequence: an I-PER cannot follow O. Under strict scoring the entity is wrong. Our softmax model made 98 such invalid transitions on the test set.

What a CRF adds

A linear-chain Conditional Random Field (Lafferty, McCallum & Pereira, 2001) scores a whole tag sequence instead of single tags. It keeps the per-word emission scores from the linear layer and adds a learned transition matrix A (7 × 7): A[i][j] is the score for tag j following tag i. It also learns start and end scores.

score(x, y) = start[y₁] + Σ_i e_(i, y_i) + Σ_(i>1) A[y_(i−1), y_i] + end[y_n] ↑ emissions (from BERT) ↑ transitions (learned by CRF) p(y | x) = exp(score(x, y)) / Z(x) Z(x) = Σ over ALL possible tag sequences y' of exp(score(x, y'))

During training, transitions that never appear in correct data (like O → I-ORG) get large negative scores. At prediction time the CRF chooses the sequence with the highest total score, so a good emission for I-PER is not enough on its own: the path must also make sense.

Training: negative log-likelihood and the forward algorithm

The loss is −log p(y_gold | x) = log Z(x) − score(x, y_gold). It goes down when the gold path's score rises relative to all other paths. The hard part is Z(x): with 7 tags and 10 words there are 7¹⁰ ≈ 282 million paths. The forward algorithm computes it with dynamic programming in O(n · K²) time: for each word and each tag, it keeps the log-sum of scores of all paths ending there, building on the previous word's values. In code this is -self.crf(emissions, clean_labels, mask=mask, reduction='mean').

Prediction: the Viterbi algorithm, worked example

Viterbi is the same dynamic programming, but with max instead of sum, plus back-pointers to recover the best path. Here is a small example with 3 tags {O, B-PER, I-PER} and invented but realistic numbers.

Complexity

Both forward and Viterbi take O(n · K²) time for n words and K tags. With K = 7 that is 49 operations per word: negligible next to BERT. Our CRF model was only about 7–20% slower at inference than softmax across runs (6.2 s vs 5.8 s in the notebook run; 8.3 s vs 6.9 s in the compare_models.py run, for all 965 test sentences on GPU).

How the library is used (pytorch-crf)

  • CRF(num_labels, batch_first=True) creates transitions (7×7), start_transitions (7) and end_transitions (7), all learned.
  • crf(emissions, tags, mask, reduction='mean') returns the log-likelihood averaged over the sentences in the batch; we negate it to get a loss.
  • crf.decode(emissions, mask) runs Viterbi and returns a Python list of tag IDs for each sentence.
  • The library requires the mask's first position to be on, which is why the code forces mask[:, 0] = True for the [CLS] position.
Panel questions§9 CRF
What is a CRF, in one sentence?

A probabilistic model that scores an entire label sequence using per-position scores plus learned scores for adjacent label pairs, and picks the globally best sequence with Viterbi.

Why is it called "conditional"? How is it different from an HMM?

It models p(y | x), the tags given the words, directly (a discriminative model). An HMM models the joint p(x, y) and must model how words are generated, with strong independence assumptions. A CRF can use any features of the whole input, here BERT's contextual vectors, without modelling the input distribution. HMMs also suffer the "label bias" problem that MEMMs have; CRFs normalise globally (over whole sequences) and avoid it.

BERT already sees the whole sentence through attention. Why does it still need a CRF?

BERT's attention makes each word's input features context-aware, but the softmax output decision is still made per word: the model never sees the tags it has chosen for neighbours. The CRF adds dependencies between output labels. In high-resource English the gain from CRF on top of BERT is often small, but in our lower-resource, noisy-label setting it was large: +12 F1 and 80% fewer invalid transitions. The biggest gain was on ORG (+20.4), the class with the longest spans.

Why not just post-process the softmax output with rules (e.g. turn O → I-X into B-X)?

Rules can repair the form of a sequence but not its content. In the Viterbi example above, the right fix is to change word 1 from O to B-PER, not to turn word 2 into B-PER; only a model that weighs both emissions and transitions knows which fix is better. The CRF learns these trade-offs, and also learns soft preferences (e.g. B-PER → I-PER is very common) that rules can't express.

What is the time complexity of Viterbi, and why not brute force?

O(n·K²). Brute force over all paths is O(Kⁿ): for 10 words and 7 tags that is about 282 million paths, versus 490 steps for Viterbi. Dynamic programming works because the best path to tag j at word i only depends on the best paths to each tag at word i−1.

Why is the CRF training loss (~4–6) so much bigger than the softmax loss (~0.5–0.9)?

They measure different things. Cross-entropy is averaged per word. The CRF loss is the negative log-probability of a whole sentence's tag sequence, averaged per sentence (reduction='mean' averages over the batch). A sentence-level log-probability is roughly a sum over its words, so it is naturally several times larger. You cannot compare the two numbers directly; compare F1 instead.

If the CRF learns to forbid invalid transitions, why are there still 20?

Because of how our CRF mask works (details in section 20). During training the mask skips continuation subwords, but pytorch-crf assumes the mask is contiguous, so some transitions it learns are between a word and a masked filler position labelled O. At inference it decodes over all subwords. This mismatch means the learned transition matrix is not exactly the word-to-word one, so a few invalid sequences survive. A fix is to run the CRF only over first-subword positions and add hard IOB2 constraints. That is our first future-work item.

What are emissions?

The 7 scores per position from the linear layer (self.classifier), before any normalisation. In CRF terminology they are the "unary" or "emission" scores: how much each tag fits that position on its own. The CRF adds transition scores to them.

Ideas explained

Gradient descent and Adam/AdamW

Training repeats: run a batch → compute the loss → backpropagation computes how each weight affects the loss (the gradient) → move each weight a little against its gradient. Adam keeps running averages of each weight's gradient and squared gradient, so every weight gets its own adaptive step size. AdamW (Loshchilov & Hutter) applies weight decay directly to the weights instead of mixing it into the gradient, which is the correct form for Adam and the standard for BERT.

Warm-up + cosine schedule

The learning rate rises linearly from 0 to 3e-5 over the first 10% of steps, then follows half a cosine curve down to 0. Early on, the new linear/CRF layer is random and produces big, noisy gradients; a small rate stops those from damaging the pre-trained encoder.

Mixed precision (FP16) and GradScaler

Inside torch.amp.autocast('cuda'), most maths runs in 16-bit floats, which is faster and lighter. Tiny gradients can underflow to zero in FP16, so GradScaler multiplies the loss by a large factor before backward(), then un-scales before the optimizer step, and skips steps that produce infinities.

The −100 label

nn.CrossEntropyLoss(ignore_index=-100) skips every position labelled −100, so special tokens, padding and continuation subwords contribute nothing to the loss. In the CRF branch the same −100s become mask = False.

Validation and checkpointing

After each epoch, evaluate_model() runs the validation set (3,618 sentences) and computes seqeval entity F1. If F1 improved, the model is saved to results/malayalam_ner_crf_model/ (CRF) or results/malayalam_ner_model/ (softmax). The test set is never used for any decision during training.

Panel questions§10 Training choices
How did you choose your hyper-parameters? Did you tune them?

We used the standard BERT fine-tuning recipe (Devlin et al. recommend lr 2e-5–5e-5, batch 16/32, 2–4 epochs) and kept them identical for both heads. We did not run a hyper-parameter search because each full run takes hours on our GPU. Because both models share all settings, the comparison between them is fair, even if neither is perfectly tuned. Hyper-parameter search across seeds is future work.

Why only 3 epochs?

Pre-trained models converge fast; most of the gain comes in the first epoch (our 8k-sentence demo reached 0.66 val F1 after one epoch). More epochs on noisy projected labels risk memorising the noise. We save the best epoch by validation F1, so extra epochs could not hurt the saved model, only cost time.

Why use only 50,000 of the 716,652 training sentences?

Compute. Training on all 716k for 3 epochs would take roughly 14× longer than our run (days on a laptop RTX 3050). 50k sentences already contain 72,655 entity mentions, enough for strong fine-tuning, and we still beat the base paper. Using the full corpus is future work. Note: our code takes the first 50k rows, not a random sample. Naamapadam's training split comes from many news/web sources; the first rows may not perfectly represent the whole, so a random sample would be a cleaner choice.

Why AdamW and not SGD?

Transformers train poorly with plain SGD; their gradients vary hugely in scale across layers. Adam's per-parameter step sizes handle this, and AdamW's decoupled weight decay is the variant used to pre-train and fine-tune BERT. It is the default in HuggingFace.

Why warm-up? What happens without it?

At step 0 the new head is random, so gradients are large and noisy. At full learning rate those updates flow into the encoder and can destroy useful pre-trained features (sometimes called catastrophic forgetting) or make training diverge. Warm-up lets the head settle first. Cosine decay then lowers the rate smoothly so the model converges.

Does FP16 reduce accuracy?

Not in practice. Mixed precision keeps a 32-bit master copy of weights and uses loss scaling, so accuracy matches FP32 training while running about twice as fast with half the activation memory. It was necessary to fit batch 32 on a 6 GB GPU.

How do you know the model isn't over-fitting?

We monitor validation loss and entity F1 after every epoch and keep the best checkpoint. The final test F1 (84.25) on a separate, human-labelled test set the model never saw confirms it generalises. Training labels are noisy projections, so the test set being clean is a strong check.

Was the training reproducible? Did you fix a random seed?

config.py defines SEED = 42 and the training notebook calls torch.manual_seed(SEED), but the script train.py does not actually set the seed. So results from train.py can vary slightly from run to run (data shuffling, dropout, head initialisation). The reported numbers come from one run. Be upfront: fixing seeds everywhere and averaging over several seeds is future work.

11Evaluation metrics

Precision, recall, F1

  • TP (true positive): an entity we predicted that is exactly right.
  • FP (false positive): an entity we predicted that is wrong (not in gold, or wrong boundary, or wrong type).
  • FN (false negative): a gold entity we missed.
Precision = TP / (TP + FP) "of what we predicted, how much was right?" Recall = TP / (TP + FN) "of what exists, how much did we find?" F1 = 2 · P · R / (P + R) harmonic mean: high only if BOTH are high

From our results: the softmax model predicted about 1,876 entities and got 1,221 right (P 65.1%, R 81.1%). The CRF predicted about 1,498 and got 1,265 right (P 84.5%, R 84.1%). There are 1,505 gold entities. The CRF predicts almost exactly as many entities as exist, which is why its P and R are balanced.

Entity-level (strict) vs token-level

Token-level metrics score each word's tag on its own. Entity-level metrics (what seqeval computes and what we report) first group tags into spans, then count a predicted span as correct only if both its start, end and type match the gold span exactly.

Token level: 2 of 4 words right (50%). Entity level: the predicted span "Kochi Metro" ≠ gold "Kochi Metro Rail Limited", so this counts as 1 FP and 1 FN, 0 TP. Strict matching punishes truncated spans twice. This explains why our ORG entity F1 (66.6) is lower than our B-ORG token F1 (77.3).

Micro, macro and weighted averages

  • Micro average: add up TP, FP, FN over all classes, then compute P/R/F1. Big classes (PER) count more. This is our headline 84.25.
  • Macro average: compute F1 per class and take the plain mean. Every class counts equally, so weak ORG pulls it down: 80.89.
  • Weighted average: per-class F1 weighted by the number of gold entities.

Token accuracy

Fraction of words whose tag is exactly right, including O. 94.08% sounds high, but remember a model that predicts O everywhere would already get ~71% on the test set. That's why accuracy is a secondary metric for NER.

Confusion matrix

A 7 × 7 table: row = true tag, column = predicted tag, each cell = number of words. The diagonal is correct predictions; everything off the diagonal is a specific kind of mistake. Section 18 reads ours cell by cell.

Panel questions§11 Metrics
Why did you report entity-level F1 instead of accuracy?

Accuracy is dominated by the O tag (71–74% of words), so it looks high even for useless models. Users care about whole entities: half a name is not useful. Entity-level F1 is the standard NER metric (CoNLL shared tasks, IndicNER, seqeval) and is the strictest common choice, so our 84.25 is a conservative number.

Why F1 and not just precision or recall?

Each alone can be gamed: predict very few entities → high precision; predict entities everywhere → high recall. F1, the harmonic mean, is high only when both are. Our softmax model shows this: recall 81% but precision 65% gives F1 72.

Micro vs macro: which did you report and why?

Our headline is micro F1 (84.25), the standard for NER. We also report macro F1 (80.89) because it treats ORG equally with PER and so exposes the weak class. Both improved by about 12 points with the CRF.

What does seqeval do? Is it strict mode?

seqeval converts each tag sequence into a set of (type, start, end) chunks and compares gold vs predicted chunks exactly; this is the method of the official CoNLL conlleval script. We call it in its default mode. In default mode, an invalid tag like O → I-ORG is still read as the start of an ORG chunk (lenient on form), but a chunk is only counted correct if its boundaries and type match exactly. seqeval also has mode='strict', scheme=IOB2, which rejects invalid chunks altogether. That stricter mode would only lower the softmax model's score further, since it makes far more invalid transitions, so it would not change our conclusion.

Why is your entity F1 lower than token accuracy?

Token accuracy counts the many easy O words. Entity F1 ignores O and requires every word of a span to be right. One wrong word in a 4-word ORG makes the whole entity wrong (and counts as both FP and FN).

How many test entities were there and how many did you get right?

1,505 gold entities (714 PER, 482 LOC, 309 ORG) in 965 sentences / 8,532 scored words. The CRF got about 1,265 exactly right out of ~1,498 it predicted.

Panel questions§12 Data
Why Naamapadam and not WikiAnn like the base paper?

WikiAnn is built automatically from Wikipedia links and consists mostly of short title fragments, not running sentences, and its test set is also automatic. Naamapadam has real sentences, is ~100× larger for Malayalam and has a human-annotated test set, so our evaluation measures real performance. It is also the benchmark used by IndicNER, so we can compare to it (81.67).

The training labels are projected automatically. Isn't that a problem?

It adds noise (wrong boundaries, missed entities), especially for ORG. But (1) the scale (716k sentences) outweighs the noise, (2) pre-trained models are fairly robust to label noise, and (3) we evaluate on the human-annotated test set, so the reported score is honest. Noise in training labels is one reason ORG scores are lower; we list it in our limitations.

Why did 9 test sentences get dropped? Doesn't that change the benchmark?

Those rows are empty or have a different number of words and tags, so they cannot be scored. load_ner_dataframe() keeps only rows where len(tokens) == len(tags) > 0. 965 of 974 rows remain (99.1%). Both our models are scored on exactly the same 965 sentences, so the comparison is unaffected.

Why is I-LOC so rare compared to I-PER?

Malayalam writes most place names as one word, often with a case suffix attached (തിരുവനന്തപുരത്ത്), so they need only B-LOC. Person names usually have two or more words (പിണറായി വിജയൻ), giving many I-PER tags.

Did you check for overlap between train and test?

We relied on the official Naamapadam splits, which are built from different sources (train from Samanantar projection, test from separately annotated text). We did not run our own duplicate check. If asked, say this is a reasonable next sanity check.

How did you handle the validation set?

We used the full official validation split (3,618 sentences) only to pick the best epoch. The test set was used once, at the end, for the reported numbers.

Panel questions§13 Literature
Why did you choose this base paper?

It is recent (2023), on Indian-language NER (a suggested course topic), includes Malayalam results we can compare against, and uses a simple, reproducible method (fine-tuned BERT + softmax). Its clear gaps (no tag dependencies, unclear subword handling, unclear metric) gave us concrete extensions to implement and measure.

A 2025 paper reports 96.45% F1. Why is yours only 84.25?

Numbers from different datasets and protocols are not comparable. That paper's dataset is not released and it doesn't specify span-level strict matching. Token-level scores, or easier in-house test sets, give much higher numbers. Our own token accuracy is 94.08%. On the public Naamapadam test set with strict span matching, the published reference is IndicNER at 81.67, and we exceed it.

You say the base paper has inconsistent numbers. Explain.

F1 is the harmonic mean of precision and recall, so it must lie between them (it is never above the larger one). The paper's Marathi ORG row shows P 84%, R 85.6% but F1 88.8%, which cannot happen. It suggests the numbers came from different runs or averaging methods. We point this out as part of the critical analysis the course asks for.

Did you reproduce the base paper exactly?

We reproduced its method (BERT encoder + independent softmax head) as our baseline, on our data and encoder, so that the CRF comparison is controlled. We did not re-run mBERT on WikiAnn. Our softmax baseline is the "base paper approach" in our experiments.

Your softmax baseline (72.23) is lower than the base paper (82.2). Why?

Different dataset (strict, human-annotated Naamapadam vs auto-labelled WikiAnn) and probably a different metric. Also our baseline uses strong class weights that cut its precision to 65%. The fair reading is: on our benchmark, the softmax head scores 72.23, and the CRF head scores 84.25 with everything else identical.

src/model.py · forward() of MalayalamBERTCRFoutputs = self.bert(input_ids=input_ids, attention_mask=attention_mask)
sequence_output = self.dropout(outputs[0])          # [batch, 128, 768] contextual vectors
emissions = self.classifier(sequence_output)        # [batch, 128, 7]  tag scores

if labels is not None:                              # ---- training ----
    mask = (labels != -100)                         # True only on first subword of each word
    mask[:, 0] = True                               # pytorch-crf needs position 0 on ([CLS])
    clean_labels = labels.clone()
    clean_labels[clean_labels == -100] = 0          # CRF can't take -100; masked anyway
    loss = -self.crf(emissions, clean_labels, mask=mask, reduction='mean')
    return ...(loss, logits=emissions)
else:                                               # ---- inference ----
    mask = (attention_mask == 1)                    # all real subwords
    preds = self.crf.decode(emissions, mask=mask)   # Viterbi
    return ...(logits=emissions, predictions=preds)

The output object is built with type('CRFOutput', (object,), {...})(), a quick way to create an object with .loss, .logits, .predictions attributes so the training loop can treat both models alike.

  1. Load 50k training + all validation records.

Panel questions§14 Implementation
Why did you write a custom CRF class instead of using a HuggingFace model?

HuggingFace's AutoModelForTokenClassification only has a softmax head; there is no built-in BERT-CRF. We wrapped the encoder (AutoModel), a linear layer and pytorch-crf's CRF in one nn.Module. For the baseline we used the ready-made class, which is exactly the base paper's architecture.

Why pytorch-crf and not your own CRF implementation?

It is a small, widely used, tested library implementing the forward algorithm and Viterbi in batched PyTorch, so it runs on GPU and supports autograd. Writing our own risks subtle numerical bugs (log-sum-exp stability) for no research gain. We understand and can explain the algorithm (section 9).

Why keep all settings in config.py?

One place to change the backbone, head, paths or hyper-parameters, so training, evaluation, inference and the app always agree. For example switching USE_CRF changes which checkpoint every script loads.

Why both a Gradio app and a FastAPI server?

Different users. Gradio gives a demo UI for humans (and the panel) in a few lines of Python. FastAPI gives a machine interface: any program, website or mobile app can send text and get JSON back. Both reuse the same MalayalamNERPredictor, so there is one model codebase.

Why use ast.literal_eval and not eval?

The CSV stores lists as strings. eval would execute any Python code inside the file, which is a security risk. ast.literal_eval only parses literals (lists, numbers, strings) and refuses anything else.

Why is the trained model not in the GitHub repo?

Each checkpoint is about 1.1 GB, beyond GitHub's 100 MB file limit, so results/ is git-ignored. The models can be re-created with train.py, or shared via Google Drive / HuggingFace Hub.

How long does training take?

On the RTX 3050 6 GB laptop GPU the short demo (8,000 sentences, 1 epoch) took about 6 minutes per head (notebook 02). Scaling up, 50,000 sentences × 3 epochs is roughly 18–20× longer, a few hours per head.

15Subword label alignment, step by step

The dataset gives one tag per word. The tokenizer produces more subwords than words (1.56×). We must decide what label each subword gets. Our rule, from src/dataset.py:

  • Special tokens ([CLS], [SEP], [PAD]) → −100
  • The first subword of a word → the word's real tag
  • Every later subword of the same word → −100

Panel questions§15 Alignment
Why label only the first subword? What are the alternatives?

Alternatives: (a) give every subword the word's label (for B-X, later pieces get I-X or B-X); (b) average the subword vectors into one word vector; (c) use the last subword. First-subword is the approach of the original BERT paper for CoNLL NER and the HuggingFace token-classification tutorial. It keeps exactly one prediction per word, so training and evaluation are both at word level, and it doesn't over-weight long words in the loss (with option a, a word split into 4 pieces would count 4 times).

Doesn't the first subword miss the information in the suffix?

No, because of self-attention: the first subword's final vector is computed by attending to all subwords, including its own continuation pieces. The suffix information flows into it through the 12 layers. The −100 only means "no loss is computed here", not "the model can't see this token".

What does −100 mean exactly?

It is PyTorch's default ignore_index for CrossEntropyLoss: positions with that label are skipped in the loss and its average. It is an arbitrary number that can't be a real class ID. For the CRF we turn it into mask = False.

How do you get back from subword predictions to word predictions at test time?

We use the same rule in reverse: take the prediction at each word's first subword (where the label isn't −100 in evaluation, or where word_idx changes in predict.py) and ignore the rest. This gives exactly one tag per original word, which is what seqeval compares.

What happens if a sentence is longer than 128 subwords?

truncation=True cuts it; the words past the cut get no prediction. In evaluation those words are simply not scored (that's why 8,532 of 8,534 test words were scored). In the app, very long inputs would lose their tail; splitting long text into sentences first would fix this. It's rare with our ~9-word sentences.

Panel questions§16 Architecture
Draw your architecture and explain each block.

Sentence → word split → WordPiece tokenizer ([CLS] … [SEP], padded to 128) → IndicBERTv2 (12 layers, 768-dim) → dropout → linear 768→7 emissions → CRF (Viterbi) → IOB2 tags per subword → keep first-subword tag per word → group into entity spans → optional DATE/CARDINAL rules.

Why dropout before the classifier?

It randomly zeroes 10% of the features during training so the classifier can't rely on any single feature, reducing over-fitting. HuggingFace's token-classification model does the same, so both heads match. Dropout is switched off at inference by model.eval().

Why a single linear layer and not an MLP or BiLSTM on top of BERT?

BERT's 12 layers already produce rich contextual features; a linear layer is enough to read the tag out of them, and it's the standard setup (BERT paper, base paper). Adding a BiLSTM between BERT and CRF sometimes helps a little but adds parameters, time and over-fitting risk. Keeping it simple also isolates the effect of the CRF.

Does the CRF see subwords or words?

In training it sees only first-subword positions (plus [CLS]) through the mask; in prediction it sees every real subword. We then keep only first-subword predictions. Section 20 explains why this mismatch matters and how to fix it.

Panel questions§18 Results
Your CRF has lower recall on I-ORG than the softmax (49% vs 76%). Isn't the CRF worse there?

At token level for I-ORG, yes: the softmax finds more I-ORG words, but it also labels 280 O words as I-ORG (precision 40%). The CRF is more conservative (I-ORG precision 77%). At the level that matters, whole entities, ORG F1 goes from 46.1 to 66.6. The CRF's remaining weakness is truncating long ORG names.

Is the +12 F1 improvement statistically significant?

We ran one training run per model, so we have no variance estimate across seeds and did not run a significance test. However, the gap is very large (12 points over 1,505 entities), consistent across all three classes and visible in the early demo run too, so it is very unlikely to be noise. A paired bootstrap test over test sentences and multiple seeds would make this rigorous; that is future work.

How much of the gain is from the CRF, and how much from removing class weights?

We cannot separate them with our current runs; the two models differ in both. The softmax's main failure (over-prediction, low precision) is partly caused by the strong weights, so an unweighted softmax would likely score higher than 72.23. The invalid-transition count (98 → 20), however, is a direct structural effect of the CRF. The clean experiment is a 2×2 ablation: {softmax, CRF} × {weights, no weights}. It's our second future-work item.

Why is PER the best class?

Most training examples (35k mentions), strong contextual cues (titles like മുഖ്യമന്ത്രി "Chief Minister", verbs like "said"), mostly 1–2 words, and distinctive name forms. PER token F1 is 94–95%.

What are the main error types? Give an example.

(1) Missed entity words (292 → O), mostly (2) truncated ORG spans (123 I-ORG → O), e.g. "Kochi Metro Rail Limited" cut to "Kochi Metro", (3) ORG names starting with a place tagged LOC (12), (4) missed multi-word locations (31 I-LOC → O). Typing errors between PER, ORG and LOC are rare (35 words).

How fast is your model?

The whole test set (965 sentences) takes about 6–8 s on the RTX 3050 GPU in batches of 32, i.e. under 10 ms per sentence. CRF decoding adds roughly 7–20% over softmax (5.8 s vs 6.2 s in the notebook run; 6.9 s vs 8.3 s in the compare_models run; timings vary with GPU state). CPU inference is slower; ONNX export is planned for that.

Your slides say "Macro-F1 81.9%" and "974 sentences". Your report says 80.89 and 965. Which is right?

Both are right for what they measure. The slide's 81.9% is the token-level macro F1 over the six entity tags from the confusion matrix (B-/I- PER/ORG/LOC), while 80.89 is the entity-level macro F1 from seqeval. The test CSV has 974 rows; 965 are valid and scored. The report uses the more precise entity-level numbers.

Did you compare with a non-neural baseline?

Not experimentally. We compare with the Fuzzy SVM result from the literature only. A simple CRF with hand-made features (suffixes, word shape) or a majority-tag baseline would be easy to add for context.

19Inference and deployment

What MalayalamNERPredictor.predict(text) does

  1. Split words with the regex [^\s.,!?()"'\-]+|[.,!?()"'\-]: a run of characters that are not spaces or punctuation is a word; each punctuation mark is its own token. It never cuts inside a word, so Malayalam glyph clusters stay intact. This mimics the dataset's tokenization, where "." and "," are separate tokens.
  2. Tokenize with is_split_into_words=True, truncation at 128, no padding (single sentence).
  3. Run the model under torch.no_grad(). CRF: Viterbi predictions. Softmax: argmax.
  4. Word-level tags: keep the prediction at each word's first subword. Confidence = the highest softmax probability of that subword's emission scores.
  5. Rule overlay (only on words the model tagged O):
    • Malayalam month names (ജനുവരി … ഡിസംബർ) → B-DATE.
    • Words with Arabic or Malayalam digits (optionally + unit words like ശതമാനം percent, രൂപ rupees, കോടി crore, ലക്ഷം lakh) → B-CARDINAL, or DATE if within 2 words of a month name.
    • Patterns like 12 - 04 - 2023 or 2023/04/12 (five tokens) → one DATE span.
  6. Group B-/I- tags into entity spans: a B- starts a new entity; an I- of the same type extends it; anything else closes it. Date spans have spaces around "-" and "/" removed.

Panel questions§19 Deployment
How is the confidence score computed? Is it a real probability?

It is the maximum softmax probability of the 7 emission scores at the word's first subword; for multi-word entities, the code averages it as it extends the span. For the CRF model this is not the CRF's true probability for that tag (that would need the forward-backward algorithm to get marginals), and neither model is calibrated. So treat it as a rough "how sure" indicator, not a probability. The report states this. Also, the span average is a running pairwise average, so later words weigh more; a plain mean would be cleaner.

Why add DATE and CARDINAL with rules instead of training them?

Naamapadam has no DATE/CARDINAL labels, so there is nothing to train on. Dates and numbers follow regular patterns (month names, digits, fixed formats), so rules are accurate and cost no training. Rules only apply to words the model left as O, so they never override PER/ORG/LOC. They are not part of any reported metric.

What happens if the user enters English or mixed text?

IndicBERTv2 also knows English, so it will still produce tags, but the model was fine-tuned only on Malayalam, so quality on English or code-mixed text is untested and likely lower.

Why FastAPI rather than Flask?

FastAPI validates input automatically with Pydantic type hints, generates interactive API docs at /docs, runs on the fast ASGI server uvicorn, and returns proper HTTP errors (400 for empty text, 500 for failures) with little code. Flask would work but needs manual validation and docs.

Could this run without a GPU?

Yes. config.DEVICE falls back to CPU and the predictor loads with map_location. A single sentence takes a fraction of a second on CPU. Exporting to ONNX and quantising to INT8 would make CPU inference faster and lighter; that's planned.

Why does the app say "displaCy"?

displaCy is spaCy's well-known entity visualiser. We styled our Gradio app after it (coloured entity boxes with labels) because the format is familiar. It's our own implementation using gr.HighlightedText, not spaCy.

What does the batch mode do with the uploaded file? Is the data stored?

It reads the .txt line by line, predicts each line, counts (entity, type) pairs and writes one CSV to the system temp folder for download. Everything runs locally; nothing is sent to an external service.

20Weak spots to defend

A careful examiner who reads the code will find these. Knowing them in advance, and admitting them calmly with a fix, scores better than being caught out. Ordered from most to least likely to come up.

1. The CRF training mask is not contiguous

In training, mask = (labels != -100) is True only at [CLS] and at the first subword of each word. For "ഉപമുഖ്യമന്ത്രി ##യാകും ." the mask looks like T … T F T … F F F: there are holes where continuation subwords sit. The pytorch-crf library assumes all True positions come first, then all False (like a padding mask). With holes:

  • When scoring the gold path, the library adds the transition from the previous position, even if that position was masked. Masked positions carry the dummy label 0 (O). So a word after a split word is scored as if it followed an O, e.g. O → I-PER inside a multi-subword person name. The model is partly trained to accept transitions it should forbid.
  • The normaliser (the sum over all paths) skips masked positions correctly, so the two parts of the loss don't treat holes the same way.
  • The "last position" used for the end transition is computed as mask.sum() − 1, which points to the wrong place when there are holes.
  • At inference the mask is the attention mask (all real subwords), so Viterbi also runs through continuation subwords, which were never real positions in training.

Effect: the learned transition matrix is an approximation, which explains the 20 invalid transitions that remain. The model still works well (84.25 F1), because emissions carry most of the information. Fix: gather the first-subword emissions into a compact word-level sequence (so the mask is contiguous), run the CRF on words, and optionally set impossible transitions (O → I-X) to −∞ so the output is always valid.

How to say it in the viva

"Our CRF runs over subword positions with a mask that skips continuation pieces. The library expects a contiguous mask, so training and decoding see slightly different paths. That's why 20 invalid transitions remain. Moving the CRF to word-level emissions with hard IOB2 constraints fixes it; it's our first future-work item."

2. Two changes at once

Softmax used class weights; CRF didn't. The +12 F1 mixes both effects. Answer: acknowledged in the report; a 2×2 ablation is planned.

3. One run, no seed in train.py, no significance test

SEED = 42 is defined but train.py never calls torch.manual_seed (the notebook does). Answer: the gap is large and consistent across classes and in the demo; multi-seed runs + bootstrap test are future work.

4. 50k sentences, and the first 50k

Only 7% of the training data, taken from the top of the file, not randomly. Answer: compute limit (6 GB laptop GPU); we still beat IndicNER's number; random sampling and full-data training are easy next steps.

5. Encoder options listed but not compared

config.py lists MuRIL and mBERT, and the README badge mentions MuRIL, but we only trained IndicBERTv2. Answer: the switch exists; a controlled comparison is future work. Don't imply we ran it.

6. Presentation slides vs the code

  • Slides say "CRF Decoder + Inverse Class Weighting". In the code the CRF is not class-weighted; weights apply only to the softmax baseline.
  • Slides report token-level numbers (macro-F1 81.9%, "974 sentences"); the report uses entity-level (80.89 macro, 84.25 micro, 965 valid sentences).
  • The app header mentions "IndicBERTv2/MuRIL"; the deployed model is IndicBERTv2 only.

7. Confidence scores are not calibrated probabilities

For the CRF they come from softmax over emissions, not CRF marginals. Span confidence is a running pairwise average. Answer: indicative only; use forward-backward marginals and temperature scaling for real probabilities.

8. Smaller code and packaging issues

  • requirements.txt lacks pytorch-crf, fastapi, uvicorn.
  • Full-run training logs were not saved (LOG_DIR is unused).
  • evaluate.py and predict.py silently fall back to the untrained pre-trained model if no checkpoint exists, which would give meaningless tags; an error would be safer.
  • The app's combine_adjacent=True merges two neighbouring entities of the same type visually (the entity table still lists them separately).
  • Single-text mode truncates at 128 subwords with no sentence splitting.
  • Batch counts treat inflected forms (കൊച്ചി / കൊച്ചിയിൽ) as different entities.
  • DATE/CARDINAL rules have no evaluation set.

9. Data-level limitations

Noisy projected training labels (hurts ORG boundaries most); only three entity types; news-style text only (not tested on social media or code-mixed Manglish).
